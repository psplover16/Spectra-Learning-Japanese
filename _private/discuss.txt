PART 1 — 候選優化 #1：單字資料 tuple 化（最高確定性）
================================================================================

【收益】約 15-20 KB（gzip 後，5 個 N 級加總）

【現狀】

src/modules/vocabulary/data/jpWords_N5.ts 開頭：

    import type { RawVocabularyEntry } from '@/modules/vocabulary/types/vocabulary';

    const jpWords_N5: RawVocabularyEntry[] = [
      {
        text: "あさ",
        romanization: "a-sa",
        kanji: "朝",
        meaning: "早上",
        stage: "N5",
      },
      ...
    ];

每筆 entry 重複 5 個 key 名稱（text / romanization / kanji / meaning / stage），
而 stage 永遠等於 "N5"（在 jpWords_N5.ts 裡），可從檔名 / import path 推導，
是純冗餘資訊。

【優化策略】

把資料改為 tuple，順序 = [text, romanization, kanji, meaning]：

    const jpWords_N5_raw: ReadonlyArray<readonly [string, string, string, string]> = [
      ["あさ", "a-sa", "朝", "早上"],
      ["ばん", "ba-n", "晩", "晚上"],
      ...
    ];

    // 在 useVocabularySession.ts 或一個專屬 mapper 裡轉回 object：
    function toEntry(tuple: readonly [string, string, string, string]): RawVocabularyEntry {
      return {
        text: tuple[0],
        romanization: tuple[1],
        kanji: tuple[2],
        meaning: tuple[3],
        stage: "N5",  // 由 importer 決定
      };
    }

    export const jpWords_N5 = jpWords_N5_raw.map(toEntry);

UI、Storage、Filter 邏輯完全不變，因為 `jpWords_N5` 對外仍是 `RawVocabularyEntry[]`。

【估算】

  - jpWords_N5.ts source：47 KB → tuple 化後估 30 KB
  - 重複 key "text:" 5 chars × ~700 筆 = 3.5 KB raw 節省
  - 5 個 key 合計 ~20 chars × 700 筆 = 14 KB raw 節省
  - 5 個檔合計 source：~130 KB → ~85 KB

  gzip 對重複字串擅長，所以實際 wire 節省會打折，但仍估有：
    - 每檔 gzip 節省 2-4 KB
    - 5 檔合計 15-20 KB gzip 節省

【風險】

  - 低。runtime mapper 寫錯 → TypeScript 型別系統會擋下
  - 既有 vitest 對 vocabulary 的測試會立刻 fail
  - 不影響 UI、不影響 storage、不影響 filter

【實作步驟（之後若要落地）】

  1. 在 src/modules/vocabulary/types/vocabulary.ts 加 tuple 型別
  2. 寫一個 toEntry mapper（含單元測試）
  3. 把 5 個 jpWords_N*.ts 改寫為 tuple 形式
  4. 在 useVocabularySession 的 loaders 套用 mapper
  5. 跑 vitest + e2e 確認 vocab 頁面行為一致
  6. 對比 dist/assets/jpWords_N*.js 與 .gz 檔大小，記錄實測收益

PART 2 — 候選優化 #2：grammarNotes 130 KB chunk 分階段載入
================================================================================

【收益】約 90-100 KB 從「進頁面立即載」延後到 idle，FCP/LCP 改善
【風險】此條若實作不慎會違反「保持相同 UI」

【現狀】

src/modules/n5Grammar/composables/useN5GrammarSections.ts:8-22：

    const defaultSectionsLoader: N5GrammarSectionsLoader = async () => {
      const [particles, fundamentals, sentencePatterns, expressions, honorifics] =
        await Promise.all([
          import('@/modules/n5Grammar/data/sections/particles'),
          import('@/modules/n5Grammar/data/sections/fundamentals'),
          import('@/modules/n5Grammar/data/sections/sentence-patterns'),
          import('@/modules/n5Grammar/data/sections/expressions'),
          import('@/modules/n5Grammar/data/sections/honorifics')
        ]);
      const merged: N5GrammarSection[] = [
        ...fundamentals.sections,
        ...honorifics.sections,
        ...sentencePatterns.sections,
        ...expressions.sections,
        ...particles.sections
      ];
      return {
        sortedN5GrammarSections: [...merged].sort((l, r) => l.order - r.order)
      };
    };

5 個檔案永遠透過 Promise.all 一起載 → Vite 看到「總是一起載」就把它們合進
同一個 chunk：grammarNotes-*.js = 130 KB。

【UI 行為觀察】

src/modules/n5Grammar/views/N5GrammarView.vue:54-126 顯示：

  - 頁面進入時，先顯示「文法資料載入中」section-card
  - 等 loadSections() 完成才把全部 section 渲染出來
  - 渲染後分成 "unfinished" 與 "finished" 兩個 zone
  - N5GrammarSectionCard 有 default-expanded prop，只有 defaultExpandedSectionIds
    內的 section 預設展開，其他預設收合

也就是說：使用者進入 N5 文法頁時，看到的是一個「載入中」狀態，然後一次顯示
全部 section（多數收合、預設展開的會打開）。

【優化策略 A：嚴守 UI 不變（保守版）】

不動。理由：

  - 當前 UI 是「一次 loading → 一次顯示全部」
  - 分階段載會變成「loading → 部分顯示 → 又有新 section 出現」
  - 嚴格判定為 UI 變化（即使是漸進式增強）

收益：0

【優化策略 B：UI 接近不變（積極版）】

把 5 個 section 拆成兩波：

  Wave 1（進頁面立即載）：
    - fundamentals + honorifics（基礎 + 敬語，預設展開最常見）
    - 合計約 1233 行 source，估 build 後 ~50 KB

  Wave 2（fundamentals 顯示完，requestIdleCallback 拉剩下 3 個）：
    - particles + sentence-patterns + expressions
    - 合計約 2574 行 source，估 build 後 ~80 KB

實作要點：

  - useN5GrammarSections 提供兩階段：loadCore() 與 loadDeferred()
  - loadCore 結束 → isLoading = false，sections 已有 fundamentals + honorifics
  - 在 onMounted 後 requestIdleCallback 觸發 loadDeferred
  - loadDeferred 完成後，把後面的 3 個 sections push 進 sections.value

UI 影響：

  - 進頁面瞬間看到的 section 數量會「先少後多」
  - 若使用者進頁面就立刻 scroll 找 particles → 可能看到尚未出現
  - 嚴格說：這是 UI 變化

收益：FCP/LCP 視覺改善 30-50%、TTI 略改善（看設備）

【優化策略 C：欺騙式 chunk 拆分（中庸版）】

維持 Promise.all 介面，但用 Vite manualChunks 強制把每個 section 拆成獨立 chunk：

    // vite.config.ts
    rollupOptions: {
      output: {
        manualChunks: {
          'vendor-vue': ['vue', 'vue-router'],
          'n5-fundamentals': [
            'src/modules/n5Grammar/data/sections/fundamentals.ts'
          ],
          // ...其他 4 個 section 各一個 chunk
        }
      }
    }

結果：grammarNotes 130 KB 變成 5 個小 chunk，仍然 Promise.all 一起載。

UI 影響：零（行為完全一致）
收益：幾乎零（瀏覽器仍然並行下載 5 個 chunk，總 wire 大小一樣）
但有副效益：未來若改成分階段，已準備好 chunk

【建議】

  - 若你嚴守「保持相同 UI」→ 不要做（策略 A）
  - 若你接受「漸進式顯示」是可接受的 UX 增強 → 做策略 B
  - 若你想保留未來彈性、不立刻拿到收益也行 → 做策略 C

我傾向不在此次優化動這條，除非你明確接受策略 B 的 UI 細微變化。

PART 3 — 候選優化 #3：main.css 內全域類別模組化
================================================================================

【收益】2-5 KB gzip（初始 CSS 縮減）
【風險】中（Tailwind @apply 跨檔解析需驗證）

【現狀】

src/styles/main.css 共 1054 行，結構：

  - line 1-48：CSS reset + root variables
  - line 49-75：練習頁的 50 音 checkbox 視覺
  - line 76-889：@layer components（870 行，所有自訂 utility）
  - line 890-1053：響應式 @media queries

「@layer components」內可粗分為：

  - app-shell-*           （骨架，全頁共用）
  - surface-card / section-card / table-shell（共用容器）
  - kana-* / practice-*   （只在 PracticeView 用）
  - route-*               （導覽元件，全頁共用）
  - grammar-*             （只在 GrammarView 用）
  - n5-grammar-*          （只在 N5GrammarView 用，line 515-710 = 195 行）
  - vocabulary-*          （只在 VocabularyView 用，line 712-888 = 177 行）
  - detail-pill / exam-modal-* （exam 相關，在 ExamModal）

問題：所有 .vocabulary-*、.grammar-*、.n5-grammar-* 都被打包在
index-*.css (45 KB) 主檔，但這些 class 只有當對應路由載入時才用得到。

【優化策略】

把 main.css 拆成多個檔，並由對應的 view 元件 import：

  src/styles/
    main.css                  ← 只留全域 + reset + variables + 跨頁共用
    routes/
      practice.css            ← .practice-* + .kana-*
      grammar.css             ← .grammar-*
      n5-grammar.css          ← .n5-grammar-*
      vocabulary.css          ← .vocabulary-*
    components/
      exam-modal.css          ← .exam-modal-* + .detail-pill

然後在每個 View 元件加：

    <script setup lang="ts">
    import '@/styles/routes/vocabulary.css';
    // ...
    </script>

Vite 會把 import 的 CSS 抽到對應 chunk 的 CSS 旁邊，初始 CSS 就只剩共用部分。

【估算】

  - 初始 CSS 45 KB → 估縮減至 25-30 KB
  - gzip 後節省約 2-5 KB（CSS 重複性高，gzip 壓縮率不錯）

【風險】

  - Tailwind @apply 跨檔解析：每個拆出去的 CSS 都會經過 PostCSS + Tailwind
    處理，理論上 @apply 仍能找到對應 utility，但需實測
  - 順序問題：原本 main.css 線性順序變多檔後，cascade 優先級可能變
  - 開發體驗：找一個 class 從一個檔變要找好幾個檔

【建議】

  - 收益偏小，風險偏高（破壞既有 styling 的可能性實際存在）
  - 比較划算的替代：寫個 dead-class 掃描 script
    （grep src/**/*.vue 看哪些 class 完全沒被引用，先刪死碼）
  - 不建議在此輪實作

PART 4 — 候選優化 #4：vocabularyMarks 持久層改 IndexedDB
================================================================================

【收益】不確定（取決於使用者實際標記量）
【風險】中（複雜度上升、async API 滲透）

【現狀】

src/shared/utils/storageGuard.ts:13-38 顯示所有 storage 都是 localStorage：

    export function readJsonStorage<T>(key, validate): T | null {
      const storage = getLocalStorage();
      if (!storage) return null;
      const rawValue = storage.getItem(key);
      if (!rawValue) return null;
      try {
        const parsed = JSON.parse(rawValue);
        if (validate(parsed)) return parsed;
      } catch { /* ignore */ }
      storage.removeItem(key);
      return null;
    }

CLAUDE.md 寫「IndexedDB（大量學習資料、字卡）」但實作仍 localStorage。

【何時 localStorage 會變慢】

  - JSON.parse / stringify 是 sync 阻塞主執行緒
  - localStorage 整個 quota ~5-10 MB
  - 一次操作通常 <1ms（小資料），但 50 KB+ 資料可能 5-20ms
  - 50ms+ 才是使用者明顯感覺得到的卡頓門檻

vocabularyMarksStorage 存的應該是「標記過的單字 ID list」。N5 約 700 字，
全標也才 700 個 ID（< 10 KB JSON），sync I/O 完全 ok。

【建議】

  - 不做。除非你實機量測有 marks 操作的明顯卡頓
  - CLAUDE.md 自己寫「使用者明顯感覺到的卡頓視為 bug」，目前沒這個 bug
  - 如果未來要做，建議只挑「大資料項」遷移（例如未來若有 SRS 排程資料），
    其他繼續用 localStorage

PART 6.1 — Part 4 motivation 補充
================================================================================

使用者已釐清 Part 4 的動機：「為未來資料量預設」。

這意味著當前 vocab marks 規模（< 10 KB JSON）並非問題本身，而是要為以下
可預見的擴張先把儲存層底子打好：

  - 未來可能加入 SRS（間隔重複）排程資料：每字一筆，含下次複習時間、
    熟練度、答對／答錯歷史 → 預估每字 100-200 bytes，N5+N4+N3 約 3000
    字時，5-10 MB localStorage quota 上限會撞到
  - 未來可能加入個別字卡的學習紀錄（每次練習時間、答題時間）→ 隨用量
    線性成長
  - 未來可能加入跨設備同步暫存區（離線寫入、上線時批次同步）

由於以上都是「目前沒做、未來想做」的事，現在動儲存層的目的是：

  - 避免「先用 localStorage 撐到撞牆才大改」的高風險路徑
  - 提早把 sync I/O 改為 async API，後續加 SRS 不必再重構業務層
  - 對齊 CLAUDE.md 的技術棧宣稱（IndexedDB 用於大量學習資料）

(本動機要寫進 proposal.md 的「Why now」段落。)
