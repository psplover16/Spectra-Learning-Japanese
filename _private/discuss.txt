本專案優化討論清單
====================

目標：讀取速度更順暢、體積更小、執行更快。
依「投入產出比（ROI）」排序，越前面越值得先做。
範疇限定在 src/、vite.config.ts、index.html、tailwind.config.ts、public/ 等專案層級設定，不動 openspec 規格內容。


────────────────────────────────────
A. 高優先級（最高 ROI，建議優先處理）
────────────────────────────────────

A1. FontAwesome 三個套件只為了一個 ✕ 圖示 → 體積最大且立即可改
- 現況：
  - dependencies 載入 `@fortawesome/fontawesome-svg-core`、`@fortawesome/free-solid-svg-icons`、`@fortawesome/vue-fontawesome` 三套。
  - 全專案僅 `src/modules/exam/components/ExamModal.vue` 使用，且只用 `faXmark` 一個圖示。
- 影響：即使 tree-shaking 也仍會把 wrapper、icon definition 與 svg-core runtime 帶進 bundle，估計可省 30~80KB（gzip 前）。
- 建議擇一：
  1. 直接以 inline SVG 取代（最小、零依賴）：
     `<svg viewBox="0 0 384 512" aria-hidden="true"><path d="M376.6 ..."/></svg>`
  2. 或保留 FontAwesome 但改為直接 import 單一圖示 SVG：
     `import xmarkSvg from '@fortawesome/free-solid-svg-icons/faXmark.svg?raw';`
- 順手：移除 package.json 三個 fortawesome 依賴，縮短 install 時間。

A2. Vite build 缺少 vendor chunk 切分策略
- 現況：`vite.config.ts` 沒有設定 `build.rollupOptions.output.manualChunks`。
- 影響：所有 node_modules（vue、vue-router、fortawesome、workbox-window）都和應用程式碼混在同一個 entry chunk，第一次進站下載量偏大；之後改 src 也會讓使用者重新下載 vendor。
- 建議：
  ```ts
  build: {
    chunkSizeWarningLimit: 500,
    target: 'es2020',          // 配合現代瀏覽器再縮一點 polyfill
    rollupOptions: {
      output: {
        manualChunks: {
          'vendor-vue': ['vue', 'vue-router'],
          // 若 fortawesome 暫時還在，獨立切出：
          'vendor-icons': [
            '@fortawesome/fontawesome-svg-core',
            '@fortawesome/free-solid-svg-icons',
            '@fortawesome/vue-fontawesome'
          ]
        }
      }
    }
  }
  ```
- 預期：vendor 長期快取命中率↑、應用程式更新時使用者只下載小 chunk。

A3. Workbox 設定可再精緻化（PWA 體驗最大化）
- 現況：vite.config.ts 的 `workbox` 只有 `globPatterns`。
- 建議補上：
  ```ts
  workbox: {
    globPatterns: ['**/*.{js,css,html,ico,png,svg,json,webmanifest}'],
    cleanupOutdatedCaches: true,
    navigationPreload: true,
    navigateFallback: appBasePath + 'index.html',
    navigateFallbackDenylist: [/^\/api\//],   // 即便目前沒 API，預先保護
    runtimeCaching: [
      {
        urlPattern: ({ request }) => request.destination === 'image',
        handler: 'CacheFirst',
        options: {
          cacheName: 'duotify-images',
          expiration: { maxEntries: 60, maxAgeSeconds: 60 * 60 * 24 * 30 }
        }
      }
    ]
  }
  ```
- 重點：
  - `cleanupOutdatedCaches`：避免歷次版本快取殘留撐大裝置儲存。
  - `navigationPreload`：讓 SW 啟動同時就送 navigation request，PWA 啟動感更快。
  - `navigateFallback`：補強離線回訪 SPA route 的 shell 行為，與目前 `route-switching-performance` 規格相容。

A4. index.html 太精簡，缺少效能 / PWA meta
- 現況：`<head>` 只有 charset、icon、viewport、title 共 4 行。
- 解決方案：直接以下整段取代 `index.html` 的 `<head>` 內容
  ```html
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0, viewport-fit=cover" />

    <!-- SEO / 分享 -->
    <title>Duotify 日語學習 PWA</title>
    <meta name="description" content="Duotify 日語學習 PWA：假名練習、文法、單字、N5 學習" />
    <meta name="color-scheme" content="light" />
    <meta name="theme-color" content="#b45a32" />

    <!-- iOS PWA -->
    <meta name="apple-mobile-web-app-capable" content="yes" />
    <meta name="apple-mobile-web-app-status-bar-style" content="default" />
    <meta name="apple-mobile-web-app-title" content="Duotify" />
    <link rel="apple-touch-icon" href="/icons/180.png" />

    <!-- favicon（B5b 同步替換完成後再改成 favicon.ico）-->
    <link rel="icon" href="/vite.ico" />

    <!-- 入口 -->
    <script type="module" src="/src/app/main.ts"></script>
  </head>
  ```
- 注意：
  - `viewport-fit=cover` 是為了支援有 notch / 圓角的 iPhone PWA 全螢幕。
  - `<script>` 從 `<body>` 搬到 `<head>` 並保持 `type="module"`，瀏覽器仍是 defer 行為，但能更早建立 module graph。
  - 若日後做 B1 方案 2（self-host Noto Sans TC），於此處補 `<link rel="preload" as="font">`。
- 影響：
  - SEO / 分享預覽 / iOS PWA 體驗一次補齊。
  - `theme-color` 同步到 manifest 之外，第一次啟動時 Android Chrome 會更穩。


────────────────────────────────────
B. 中優先級（值得安排，但需配合驗證）
────────────────────────────────────

B1. 字型策略未明確
- 現況：`src/styles/main.css` 設 `font-family: "Noto Sans TC", "Segoe UI", sans-serif;`，但專案未引入 Noto Sans TC web font。經 grep 確認全 src 無 `@font-face`、無 fontsource。
- 影響：在沒裝 Noto Sans TC 的裝置（多數 Windows 預設沒裝），實際走第二順位 Segoe UI。意圖不明確。
- 解決方案（擇一）：

  方案 1（推薦，最省事）：放棄 Noto，改成意圖清楚的系統字型 stack
  改 `src/styles/main.css` 第 8 行：
  ```css
  font-family:
    system-ui,
    -apple-system,
    "Segoe UI",
    "Hiragino Sans",
    "Hiragino Kaku Gothic ProN",
    "Microsoft JhengHei UI",
    "PingFang TC",
    "Helvetica Neue",
    Arial,
    sans-serif;
  ```
  - 中文/日文/英文都用各 OS 原生字型，零下載、零 FOUT。
  - 對「日語學習 PWA」這類純文字應用最划算。

  方案 2：真的要用 Noto Sans TC → self-host 子集化
  ```bash
  npm install @fontsource/noto-sans-tc
  ```
  在 `src/styles/main.css` 最上方加：
  ```css
  @import "@fontsource/noto-sans-tc/400.css";
  @import "@fontsource/noto-sans-tc/700.css";
  ```
  並補 `font-display: swap`：
  ```css
  @font-face { font-display: swap; }   /* fontsource 已預設，但顯式宣告較安全 */
  ```
  並在 `index.html` 對首屏權重加 preload（檔名以實際 build 為準）：
  ```html
  <link rel="preload" href="/assets/noto-sans-tc-latin-400.woff2" as="font" type="font/woff2" crossorigin />
  ```
  - 缺點：Noto Sans TC 全集 ~2MB，即使子集化中文常用字仍 200~500KB，會拖長首次下載。
  - 若不能放棄，務必走 `unicode-range` 子集，且只 preload latin/常用 CJK 一段。

B2. N5 文法資料 `grammarNotes.ts` 約 176KB（最大單檔）
- 現況：已由 `useN5GrammarSections` 動態 import，shell-first 載入（OK）。
- 建議：
  - 確認 build 後實際 chunk 大小是否仍 < 500KB 警戒線。
  - 若想再壓：依 v11~v16 章節再切多個檔案，由 composable 依當前可見 section 漸進載入；好處是進入頁先解析較少 JS，缺點是要稍動 type/聚合。
  - 或保留現狀 + 在 idle 時 prefetch，讓瀏覽器空檔就抓好。

B3. 路由 preload 與 KeepAlive 的實際成本還沒看見
- 現況：`AppShell.vue` 在 mounted 後 idle preload 主要 route component（架構文件已述）。
- 建議：
  - 加入 `rollup-plugin-visualizer`（dev only）量化 preload 收益與 chunk 分布：
    ```ts
    import { visualizer } from 'rollup-plugin-visualizer';
    plugins: [..., mode === 'analyze' && visualizer({ filename: 'dist/stats.html', gzipSize: true, brotliSize: true })]
    ```
  - 跑 `vite build --mode analyze` 看 chunk graph，再決定要不要進一步 split。

B4. 預先壓縮（pre-compression）
- 現況：未啟用。
- 建議：加入 `vite-plugin-compression` 同時產 `.gz` 與 `.br`：
  ```ts
  import viteCompression from 'vite-plugin-compression';
  plugins: [
    ...,
    viteCompression({ algorithm: 'gzip', ext: '.gz' }),
    viteCompression({ algorithm: 'brotliCompress', ext: '.br' })
  ]
  ```
- 注意：GitHub Pages 不支援自選編碼回應 `.br`，但若日後改 Cloudflare Pages / Netlify / Vercel 就直接受惠；GitHub Pages 仍會 on-the-fly gzip。

B5. PWA icons 體積
- 現況（已驗證為 8-bit RGBA non-interlaced PNG）：
  - `public/icons/512.png` ≈ 148KB（512×512）
  - `public/icons/192.png` ≈ 32KB（192×192）
  - `public/icons/180.png` ≈ 28KB（180×180）
- 解決方案：

  Step 1（無損壓縮，先做）：
  ```bash
  # 安裝 oxipng（任一）
  npm install -g oxipng
  # 或 cargo install oxipng
  # 或 scoop install oxipng

  # 對所有 PWA icon 做最強無損壓縮，原檔備份
  oxipng -o max --strip safe -i 0 -p public/icons/512.png
  oxipng -o max --strip safe -i 0 -p public/icons/192.png
  oxipng -o max --strip safe -i 0 -p public/icons/180.png
  ```
  預期：512 從 148KB → 約 90~110KB，省 ~30%。

  Step 2（有損壓縮，視覺允許再做）：
  ```bash
  npm install -g pngquant-bin
  pngquant --quality 80-95 --strip --force --output public/icons/512.png public/icons/512.png
  pngquant --quality 80-95 --strip --force --output public/icons/192.png public/icons/192.png
  pngquant --quality 80-95 --strip --force --output public/icons/180.png public/icons/180.png
  ```
  預期：512 再從 ~100KB → 50~70KB；icon 在裝置桌面不容易看出色階差異。

  Step 3（可選）：補 maskable icon
  - 重新匯出一張 maskable 安全區（safe zone 80%）的 512.png 命名為 `512-maskable.png`。
  - 在 `vite.config.ts` 的 `pwaIconDescriptors` 補一筆：
    ```ts
    { src: 'icons/512-maskable.png', sizes: '512x512', type: 'image/png', purpose: 'maskable' }
    ```
  - 效果：Android 安裝後 icon 不會被裁切成圓形時邊緣留白。

  驗收：build 後 `dist/icons/*.png` 容量比較表貼回 PR。

B5b. favicon `public/vite.ico` 過大（新發現）
- 現況：`public/vite.ico` 是 256×256 的 PNG-in-ICO，超過實際 favicon 需求；`index.html` 引用 `/vite.ico`。
- 影響：每次冷啟動瀏覽器都會抓這顆 favicon，雖然會被快取但首次仍是純浪費。
- 解決方案：
  ```bash
  # 用既有 192.png 縮成 32×32 + 16×16 的多尺寸 ico
  # （任一工具：ImageMagick / png-to-ico / 線上 realfavicongenerator）
  magick public/icons/192.png -define icon:auto-resize=64,48,32,16 public/favicon.ico
  ```
  並改 `index.html`：
  ```html
  <link rel="icon" type="image/x-icon" href="/favicon.ico" sizes="any" />
  <link rel="icon" type="image/svg+xml" href="/icons/icon.svg" /> <!-- 可選 -->
  ```
  順手把 `public/vite.ico` 移除，並更新 `src/shared/config/publicAssets.ts` 的 `faviconFileName`。
  注意：`tests/unit/publicAssets.spec.ts` 有驗證 favicon 是否存在於 build 輸出，要同步改。

B6. 未使用的 scaffolding 素材
- 現況（已用 grep 驗證 src/ 內無任何引用）：
  - `src/assets/vue.svg`（1KB）→ Vite scaffold 殘留
  - `src/assets/vite.svg`（12KB）→ Vite scaffold 殘留
  - `src/assets/hero.png`（44KB）→ 沒有 import / `<img src>` / CSS url() 引用
- 解決方案：

  Step 1（直接刪除三個檔案）：
  ```bash
  git rm src/assets/vue.svg src/assets/vite.svg src/assets/hero.png
  ```

  Step 2（驗證沒踩到雷）：
  ```bash
  npm run typecheck
  npm run lint
  npm run test:unit
  npm run build       # 確認 build 沒有抱怨缺資產
  ```

  Step 3（順手評估整個 src/assets/）：
  - 刪掉三個檔案後 `src/assets/` 變空目錄；可一併 `rmdir src/assets`。
  - 若 PROJECT_ARCHITECTURE.md 第 60~63 行還列著這三張圖，順手更新文件。

  Step 4（若日後真的要放圖）：
  - 入站圖片 < 4KB 用 SVG 行內或 `import xxx?inline`。
  - 大過 8KB 一律走 `public/` 或 `import xxx?url` + `loading="lazy" decoding="async"`。
  - 照片類資產轉 WebP 或 AVIF（省 30~60%）。


────────────────────────────────────
C. 低優先級（小幅但 nice-to-have）
────────────────────────────────────

C1. `build.target` 顯式宣告
- Vite 7 預設 target 偏保守，可改 `'es2020'` 或更新，省下不必要的 polyfill 與 helper（配合 A2 一次設定即可）。

C2. CSS 路由特化集中過多在 `main.css`
- 現況：`src/styles/main.css` 裡塞了 `/practice`、`/grammar`、`/vocabulary`、`/n5-grammar` 多個 route-specific 樣式。
- 風險：所有路由都得載入完整 CSS，且修改某 route 樣式時 cache 全失效。
- 建議：把 route-specific 區塊搬進對應 view 的 `<style scoped>` 或 `style.css`，由 Vue/Vite 自動以 route component 切分。
- 注意：要小心 selector 範圍，避免破壞 `RouteOwnership.spec.ts` 既有的 negative ownership 規則（N5 不外溢的測試）。

C3. main.ts 啟動順序
- 現況：
  ```ts
  createApp(AppShell).use(router).mount('#app');
  void triggerLaunchUpdateCheck();
  ```
- 建議：把 `triggerLaunchUpdateCheck()` 包在 `requestIdleCallback` / `setTimeout(..., 0)` 內，徹底讓首屏 paint 不被 PWA registration 阻擋（雖然目前已 fire-and-forget，但可再保險）。

C4. TypeScript 增量編譯
- `npm run build` 目前是 `vue-tsc --noEmit -p tsconfig.app.json && vite build`，已先 typecheck 再 build。
- 可考慮以 `vue-tsc --build`（incremental）+ `tsbuildinfo` 加速 CI 第二次 build；本機 dev 沒影響。

C5. 圖片載入屬性
- 全專案若有 `<img>`，建議統一加 `loading="lazy"` 與 `decoding="async"`（hero/icon 區除外）。
- N5 / 文法表格目前看起來純文字 + svg，影響不大，但養成規範比較不會出意外。

C6. 觀察指標自動化
- 加入 Lighthouse CI 或在 e2e 蒐集 `performance.getEntriesByType('navigation')` 的 TTFB / FCP / LCP，建立基線。
- 配合現有 `route-switching-performance.spec.ts`，可逐步追蹤改動是否真的提升。

憲法合規性檢查（必讀，動工前先處理）
────────────────────────────────────

本檔目前是「探索性討論」，不是 Spectra change proposal。依照 `constitution.md` 與 `openspec/config.yaml`，下列項目在轉成正式變更前必須補齊。

【流程強制】
- 憲法 Workflow：「Every meaningful change MUST be traceable to a specification or explicit maintenance task」。本檔列的每一項要動工前都應走 `/spectra-propose`，產出 `openspec/changes/<id>/{proposal.md,design.md,tasks.md}` 與必要的 spec delta，不能直接改 code。
- 憲法 V：任何更動「repository structure, file responsibilities, shared modules, route composition, test structure, or deployment structure」必須在同一個 work item 更新 `PROJECT_ARCHITECTURE.md`。

【依規格回寫，逐項檢查】

A1（移除 FontAwesome）
- 屬於內部重構：`ExamModal` 對外行為（關閉、emit、a11y）應維持不變，可不回寫 spec。
- 但 `tests/component/ExamModal.spec.ts` 必須在 PR 內驗證關閉鈕仍可被 a11y 名稱定位（避免從 `aria-label="關閉"` 退化為純圖示）。
- bundlephobia 不適用（是移除依賴）。

A2（manualChunks + `target: 'es2020'`）
- 「行動優先」場景需驗證：iOS Safari ≥14、Android Chrome ≥85 對 es2020 全支援，OK；但仍須在 design.md 內記錄目標瀏覽器矩陣（憲法 IV 要求量化效能影響）。
- 純 build 設定，無 spec 行為變更。

A3（Workbox `cleanupOutdatedCaches` / `navigationPreload` / `navigateFallback`）
- ⚠️ 高風險：`openspec/specs/pwa-update-check-on-launch/spec.md` 與最近合併的 `fix-pwa-update-cache-retention`（commit `972e41d`）對「更新時保留離線快取」有明確契約。
  `cleanupOutdatedCaches: true` 預設會清掉前一版本 precache，可能與該 spec 的「保留」要求衝突。
- 動工前必做：
  1. 讀 `openspec/specs/pwa-update-check-on-launch/spec.md` 與該變更歸檔的 design.md，確認 cleanup 行為是否被允許。
  2. 若需放行 → 同一 work item 更新該 spec；若不允許 → 改用更精準的 cache versioning，或拿掉 cleanupOutdatedCaches。
- `tests/e2e/pwa-offline-route-cache.spec.ts` 是這條路徑的回歸守門員，必跑。

A4（index.html meta + `viewport-fit=cover`）
- `viewport-fit=cover` 影響 iPhone notch 區的 layout，是使用者可見變更 → 應在 PR 內加 e2e 驗證手機 375px 下不破版（既有 `practice-layout.smoke.spec.ts` / `n5-grammar-layout.spec.ts` 涵蓋；確認可以通過或補一條）。
- `<meta theme-color>` 與現有 `manifest.theme_color: '#b45a32'` 須一致，避免雙來源漂移。

B1（字型策略）
