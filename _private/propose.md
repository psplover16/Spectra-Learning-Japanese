# 路由切換卡頓原因與改善方向

## 目前可能原因

本專案的 `src/app/router.ts` 已經使用 Vue Router 動態 import，因此路由切換卡頓不太像是「完全沒有 lazy loading」造成，而比較可能是以下幾個因素疊加：

- 首次進入某個 route 時，瀏覽器仍需要下載、解析並執行該頁面的 JavaScript chunk，使用者點擊後才開始載入就會感覺等待。
- 部分頁面資料量較大，例如 `src/modules/n5Grammar/data/grammarNotes.ts` 檔案偏大，切到 `/n5-grammar` 時會增加首次載入與渲染成本。
- 單字頁雖然已把 N1 到 N5 字彙資料拆成動態 import，但 `selectedJlptLevels` 預設包含所有等級，進入 `/vocabulary` 時仍可能同時載入與處理多個資料檔。
- 路由切換時 `RouterView` 會卸載舊頁並掛載新頁，若沒有保留狀態，返回已看過的頁面也可能重新建立元件、重跑 computed 與資料載入流程。
- 表格、文法卡片等頁面 DOM 量較大，切換時重新渲染大量節點會讓低階手機或行動瀏覽器更容易感到卡頓。
- PWA 的靜態資產快取若沒有涵蓋 route chunk，離線或弱網路下首次切頁可能會出現更明顯等待。

## 可選改善方法

### 方案一：導覽前預載 route chunk

在使用者對路由按鈕做出 hover、focus 或 touchstart 時，提前呼叫該頁面的動態 import，讓真正點擊時 chunk 已經開始載入或載入完成。

適合解決：

- 第一次點進某個頁面時的明顯等待。
- 桌機 hover 或手機 touchstart 到 click 之間的短暫空檔。

優點：

- 改動小，風險低。
- 不改變畫面行為與資料邏輯。
- 很適合作為第一步嘗試。

缺點：

- 只能改善 route chunk 載入等待。
- 若卡頓主因是大量資料處理或 DOM 渲染，效果有限。

### 方案二：對高頻頁面加上 KeepAlive 或狀態保留

讓常切換的頁面在離開後不要完全卸載，回來時可沿用既有元件狀態，減少重新掛載與重新計算。

適合解決：

- 從 `/vocabulary`、`/practice`、`/n5-grammar` 切走再切回來仍會卡的問題。
- 使用者希望返回頁面時保留搜尋、篩選、展開段落或滾動附近狀態。

優點：

- 對「返回已看過頁面」通常很有效。
- 可改善重複建立大型頁面 DOM 的成本。

缺點：

- 會增加記憶體使用。
- 需要處理頁面生命週期，例如 `onMounted` / `onBeforeUnmount` 可能要改成 `onActivated` / `onDeactivated`。
- 單字頁有 body scroll lock，若直接 KeepAlive，必須確認切頁後不會留下鎖定副作用。

### 方案三：重資料分段或按需載入

把大型資料與非立即可見內容延後處理。例如單字頁先載入預設等級或目前勾選等級，其餘等級背景載入；N5 文法頁先顯示可見段落，較重內容等使用者展開或空閒時再處理。

適合解決：

- `/vocabulary` 初次進入時一次處理 N1 到 N5 資料造成卡頓。
- `/n5-grammar` 因大型文法資料與大量卡片一起渲染造成卡頓。

優點：

- 最有機會改善真正的主因。
- 對手機瀏覽器與低階裝置較有感。

缺點：

- 改動比預載 chunk 大。
- 需要補 loading、empty、error 狀態。
- 需要測試確保資料延後載入不影響搜尋、篩選、註記與測驗行為。

### 方案四：降低一次渲染的 DOM 數量

針對大量表格或卡片內容，改成分頁、只渲染展開內容，或導入虛擬列表概念，避免路由切換瞬間建立過多 DOM。

適合解決：

- 單字表格列數很多時的渲染卡頓。
- N5 文法頁一次出現太多完整內容時的渲染壓力。

優點：

- 對大型清單與表格是根本改善。
- 可降低記憶體與 layout/repaint 成本。

缺點：

- UI 行為可能改變，需要決定是否接受分頁、延遲展開或虛擬列表。
- 虛擬列表若手寫會增加複雜度；若引入套件需評估 bundle 大小。

### 方案五：加入路由效能檢查與 bundle 檢查

用測試或腳本確認主要路由切換時不出現空白、不噴 console error，並在 build 後檢查 chunk 是否超過 500 KB 警戒線。

適合解決：

- 避免之後新增內容時又讓路由切換變慢。
- 讓「是否改善」有可驗證依據，而不是只靠主觀感覺。

優點：

- 能防止效能退化。
- 和專案既有 Playwright、Vitest、Vite build 流程相容。

缺點：

- 它本身不是直接優化，只是量測與防線。
- 仍需要搭配前面至少一種實際改善方案。

## 建議採用順序

1. 先做方案一：導覽前預載 route chunk，改動最小，能快速驗證首次切頁等待是否改善。
2. 若返回頁面仍卡，再做方案二：對高頻頁面加 KeepAlive 或狀態保留。
3. 若 `/vocabulary` 或 `/n5-grammar` 仍明顯卡，做方案三：重資料分段或按需載入。
4. 如果資料分段後仍是表格或卡片渲染太重，再評估方案四：降低一次渲染的 DOM 數量。
5. 無論選哪個實作方案，都建議補方案五：建立路由切換與 chunk 大小檢查，避免之後退化。

## 目前傾向

建議先從「方案一 + 最小量測」開始。若效果明顯，就先停在低風險解法；若還卡，再針對 `/vocabulary` 與 `/n5-grammar` 做資料載入與渲染優化。
